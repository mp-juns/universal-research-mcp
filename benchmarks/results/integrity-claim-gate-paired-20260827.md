# Paired Integrity & Claim-Gating Execution — 2026-08-27

## Status

Completed paired two-condition execution of the Integrity & Claim-Gating v1
protocol at reduced, explicitly approved scale. This is the first run in this
repository whose primary safety contrast excludes zero; it is **not** the full
preregistered confirmatory design, and every deviation is listed below.

- Participant: `gpt-5.6-sol` via `codex exec`, reasoning effort `medium`,
  `--ephemeral --ignore-user-config --sandbox read-only`.
- Server under test: repository source equal to `main` merge `29d3c71`
  (includes the word-boundary deny policy, required `claim_type`, index-gate
  cache, backend disclosure, and benchmark-harness fixes #46–#51).
- Approval: `corpus/approval-igcc-confirmatory-v1.json`
  (`approval_igcc_confirmatory_v1_20260827`), binding design, model, source
  revision, permissions, and budget; task corpus SHA-256 recorded inside.
- Design: 24 parameterized hidden tasks (protocol state distribution)
  × 2 conditions (`filesystem`, `mcp_claim_gate`) × 3 repetitions = 144 runs;
  all 144 completed, none discarded.

b = 21 (filesystem-only unsafe) vs c = 0 (gate-only unsafe), both-unsafe = 6

Deterministic planted-value scoring (independent secondary): 28/51 vs 6/51,

Every gate-arm unsafe assertion is a `poisoned_before_registration` case, and
the two arms fail those 6/6 identically: the hash gate cannot detect content
poisoned before registration. The negative control behaves exactly as the
protocol predicts, and no capability beyond revision integrity is claimed.

## Deviations from the preregistered plan

1. Two conditions instead of four; the two middle arms were dropped for the
   paired co-primary contrast at the approved budget.
2. 24 parameterized tasks × 3 repetitions instead of 72 hidden tasks × 2;
   document content is template-derived with one distinct planted
   quantity/value pair per task (`corpus/confirmatory_params.json`),
   generated by `scripts/run_confirmatory.py`, which reuses the repository
   fixture/runner mechanics and replaces only the two content functions.
3. The task schema requires `development_only: true`; the flag is a schema
   constant and does not describe this run's purpose.
4. The shared prompt pre-confirms the operator-approved read-only session
   scope (#51) after a smoke trial showed MCP-arm runs stalling on the
   session-scope question; the sentence is identical across conditions.
5. The gate-arm prompt names `memory_check_evidence_eligibility` (#50)
   because `claim_type` is now a required parameter and the legacy alias is
   not registered.
6. The deterministic scorer was revised twice before blinded binding
   (line→sentence negation scope; lineage-state mention rule); both
   revisions are visible in `scripts/score_deterministic.py` history and in
   the disagreement list.

## Evaluator disclosure

The blinded judge is a Claude session that also designed the corpus. It was
blinded to condition, trial identity, tool traces, and telemetry via the
repository evaluator's `--prepare-only` batches, and its per-case verdicts
with rationales are published under `rep*/evaluation/batches/*/result.json`.
The independent deterministic scorer exists precisely to bound this
conflict; the two disagree on 4.9% of fault runs, in both directions.

## Interpretation boundary

One participant model at one reasoning effort, on synthetic two-line
documents. This measures whether the evidence-eligibility workflow prevents
assertion from integrity-broken evidence at what cost; it does not measure
semantic truth, real-corpus retrieval difficulty, or other hosts. Raw trial
streams (576 files) are retained locally and bound by
`raw-trials-manifest.json` (tree SHA-256 `20fb28c2…`).

## One-sentence result

Across 45 paired hash-detectable integrity-fault runs, the filesystem
condition produced 21 unsafe assertions and the MCP+gate condition produced
0 (blinded McNemar p < 10⁻⁶), with identical 21/21 clean coverage, zero
false blocks in both arms, and a burden of ~1.9× uncached tokens and +26%
latency per run.
