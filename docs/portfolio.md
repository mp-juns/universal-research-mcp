# Universal Research MCP — 면접 설명

**기준 버전: v0.8.4 · 기능 동결 · 문서와 시연 중심**

이 문서는 면접에서 사용할 설명 초안이다. 구현한 경계, 실제 관찰한 결과,
아직 검증하지 못한 부분을 구분한다. 기능 확장 계획이나 실험 실행 승인이 아니다.

## 한 문장 소개

연구 에이전트가 찾은 문장을 근거로 사용하기 전에 원본 파일의 버전과 정확한
인용 범위를 다시 확인하고, 연구 기록의 변경에는 별도 승인을 요구하는 MCP입니다.

## 60초 설명문

> 연구 자료를 검색하는 것만으로는, 그 자료가 지금도 같은 내용인지 또는 정확히
> 어느 부분을 인용했는지 보장하기 어렵습니다. Universal Research MCP는 이
> 연결을 확인할 수 있도록 만든 연구 메모리 도구입니다.
>
> 검색 결과는 먼저 후보로만 반환합니다. 중요한 주장에 쓸 근거는 이벤트 ID,
> 파일 경로, 줄 범위, SHA-256을 묶어서 확인하고 원본을 다시 읽습니다. 파일이
> 바뀌었거나 등록된 범위와 다르면 근거 적격성 검사를 통과하지 못합니다.
>
> 기록은 추가 전용 JSONL에 남기고 검색 인덱스는 다시 만들 수 있게 분리했습니다.
> MCP의 기록 변경은 외부 승인과 복구 가능한 트랜잭션을 거칩니다.
>
> 다만 이 검사는 문장의 의미나 과학적 진실을 판정하지 않습니다. 공개 합성 실험에서
> 일부 안전성 신호와 토큰·시간 증가를 관찰했지만, 일반적인 성능 개선은 입증하지
> 못했습니다. v0.8.4를 기능 동결 기준으로 두고 이 범위를 명확히 설명하고 있습니다.

말하기 속도에 따라 소요 시간은 달라진다. 위 설명문은 약 1분 분량의 초안이며,
실제 발표나 음성 녹화를 측정한 기록은 아니다.

## 핵심 설계 결정 세 개

| 결정 | 선택 이유 | 감수한 비용과 대안 |
| --- | --- | --- |
| **원본 기록과 검색 인덱스 분리** | 인덱스 복구가 연구 이력 수정으로 이어지지 않게 한다. | SQLite만 원본으로 두는 방식보다 최신성·출처 확인이 늘어난다. |
| **외부 승인 + 복구 가능한 기록 추가** | 여러 파일을 수정하다 실패해도 같은 승인·같은 내용만 복구하게 한다. | 단순 append보다 상태 관리가 복잡하다. 여러 파일의 동시 원자성을 주장하지 않는다. |
| **공개 배포 범위를 좁게 유지** | 구현 실험과 지원 약속을 구분하고 Codex 통합 경계를 명확히 한다. | 다양한 생성 모델 제공자를 곧바로 지원하지 않는다. 저장소의 프로토타입은 공개 API가 아니다. |

## 실험을 설명할 때

**말할 수 있는 것:** 공개 합성 과제 24개를 네 조건에서 한 번씩 실행한 개발
실험이 있다. 오류 상황 18개에서 부적절한 중요 주장은 파일 검색 조건 4건,
근거 적격성 검사 포함 조건 2건이었다. 후자는 평균 토큰 1.55배, 시간 1.61배를
사용했다. 두 조건의 차이에 대한 95% 구간은 −33.3~+11.1%p로 0을 포함했다.

**함께 밝혀야 하는 것:** 별도 평가자도 LLM이었으며 인간 평가가 아니다.
근거 적격성 검사 조건에서도 상충하는 자료와 의미상 무관한 자료에 실패했다.
이는 과거 개발 실험이지, 배포된 v0.8.4의 효과를 직접 측정한 결과가 아니다.

**말하면 안 되는 것:** “환각을 절반으로 줄였다”, “연구 정확도가 입증됐다”,
“432회 벤치마크를 완료했다”, “테스트 통과 수가 실험 성공 수다”.
서로 다른 파일럿을 합쳐 하나의 표본 수나 성공률로 제시하지 않는다.

## 예상 질문과 답변

### 일반적인 RAG와 구현상 어떤 차이가 있나요?

이 프로젝트에서는 검색 후보와 근거 적격성 결과를 별도의 계약으로 둡니다.
원본의 등록된 줄 범위와 현재 파일 해시를 다시 확인해야 합니다. 다른 RAG가
이 검사를 할 수 없다는 뜻은 아니고, 이 저장소가 명시적으로 구현한 경계입니다.

### 해시가 같으면 답도 맞나요?

아닙니다. 같은 버전의 파일을 읽었다는 뜻입니다. 자료의 관련성, 자료 사이의
충돌, 자료 자체의 진실성은 별도 검토가 필요합니다. 적격성 응답에도
`claim_verified`, `semantic_support_checked`, `conflict_checked`,
`source_truth_checked`가 `false`로 남습니다.

### 저장 도중 실패하면 어떻게 되나요?

MCP의 여러 파일 기록 추가는 저널에 승인된 내용과 파일별 변경 전후 해시를
묶습니다. 일부만 반영되면 `recovery_required` 상태로 남고 같은 트랜잭션만
복구할 수 있습니다. 관리 CLI와 MCP는 같은 기록 잠금을 사용합니다.
파일별 교체와 복구를 제공하며 여러 파일이 동시에 바뀌는 원자성은 주장하지 않습니다.

### 현재 가장 분명한 한계는 무엇인가요?

근거의 의미를 자동으로 증명하지 못하고, 공개 합성 실험만으로 일반적인
성능 우위를 주장할 수 없습니다. 호스트 밖의 임의 프로세스를 통제하는 전역
보안 장치도 아니며, 다중 사용자 운영 서비스의 인증·격리를 대신하지 않습니다.

### 지금 서비스에 바로 도입할 수 있나요?

정의된 로컬 사용 범위에서 검토할 수 있지만 운영 성숙도를 과장하지 않습니다.
인터넷 공개나 여러 사용자 운영은 인증, 접근 범위, 모니터링, 장애 대응을
별도로 설계·검토해야 합니다. 1분 설명형 데모는 운영 검증 자료가 아닙니다.

## 면접 시연 순서

1. [1분 데모](demo.md)로 검색 → 원문 확인 → 적격성 → 호스트 검토를 보여준다.
2. [아키텍처](assets/architecture-overview.svg)에서 원본·기록·인덱스의 경계를 설명한다.
3. 위 설계 결정 세 개 중 질문과 관련된 하나의 대안과 비용을 설명한다.
4. 실험 결과를 말할 때 분모, 추가 비용, 신뢰구간과 미완료 범위를 함께 제시한다.

v0.8.4 이후 코드는 명확히 재현되는 버그에 한해 변경한다. 새 기능, 새 제공자
통합, 추가 벤치마크는 현재 포트폴리오 문서 정리 범위에 포함하지 않는다.
